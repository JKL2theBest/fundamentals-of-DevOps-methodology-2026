## Часть 1: CI/CD Пайплайны (GitHub Actions)

В рамках первой части написаны два конфигурационных файла для GitHub Actions. В "плохом" файле собраны критические антипаттерны, которые часто встречаются у джунов. В "хорошем" они исправлены по стандартам Enterprise-разработки.

### Анализ антипаттернов (`bad-ci.yml` vs `good-ci.yml`)

1. **Запуск деплоя при сломанных тестах (`if: always()`)**
   *В чем проблема:* В плохом пайплайне шаг деплоя запускается независимо от успеха предыдущих шагов (я специально сымитировал падение через `exit 1`). Нерабочий код улетит на прод.
   *Как исправлено:* В хорошем пайплайне процесс разбит на 5 строгих этапов (`lint`, `test`, `security`, `build`, `deploy`). Выстроена топология зависимостей: этап `deploy` ждет успешного завершения `build` через `needs: build`.
2. **Секреты в логах и хардкод**
   *В чем проблема:* Токен прописан прямо в файле пайплайна и выводится через `echo`. Это моментальная компрометация.
   *Как исправлено:* Использован механизм GitHub Secrets. Переменная безопасно прокидывается в `env`, а сам GitHub автоматически замаскирует её звездочками, если она случайно попадет в stdout.
3. **Плавающие теги экшенов (`actions/checkout@master`)**
   *В чем проблема:* Если автор экшена сломает ветку `master` или внедрит вредоносный код, наш пайплайн сломается неявно. Это классический вектор Supply Chain Attack.
   *Как исправлено:* Версия жестко зафиксирована по стабильному релизу (`actions/checkout@v4`).
4. **Отсутствие лимитов (Timeouts & Concurrency)**
   *В чем проблема:* Если процесс зависнет, он будет сжигать минуты GitHub Actions до упора. Если разработчик быстро сделает 5 пушей, запустится 5 параллельных деплоев, что вызовет гонку состояний (race condition).
   *Как исправлено:* Добавлены `timeout-minutes: 5` и блок `concurrency` (отменяет старые сборки при новых пушах в ту же ветку).
5. **Отсутствие кэширования**
   *В чем проблема:* Каждый запуск скачивает библиотеки из интернета с нуля.
   *Как исправлено:* Включено встроенное кэширование `cache: 'pip'`.
6. **Избыточные права (Permissions)**
   *В чем проблема:* По умолчанию токен `GITHUB_TOKEN` имеет слишком широкие права.
   *Как исправлено:* Задан принцип наименьших привилегий: `permissions: contents: read`.

## Часть 2: Работа с секретами (HashiCorp Vault)

Для демонстрации работы с выделенными системами управления секретами (Secret Management Solutions) локально поднят кластер HashiCorp Vault и Python-сервис, запрашивающий пароль от БД.

### Архитектурные нюансы демонстрации
1. **Dev Mode:** Для упрощения локального запуска в `docker-compose.yml` включен режим разработчика (`VAULT_DEV_ROOT_TOKEN_ID`). В реальном production рут-токены никогда не прокидываются через env-переменные.
2. **Разделение ролей:** Архитектурно правильно, чтобы приложение имело права *только на чтение* (Read-policy), а секреты закладывались администратором (Admin-policy). В скрипте `app.py` обе эти роли объединены исключительно для того, чтобы весь стенд запускался одной командой `docker-compose up`, но в коде они строго разделены комментариями.
3. **Отказоустойчивость:** Вместо антипаттерна `time.sleep()` реализован Production-style retry loop, который опрашивает API Vault до момента его готовности.
4. **Retry Loop vs Depends_on:** Директива `depends_on` в Docker Compose гарантирует только факт старта контейнера Vault, но не готовность его API принимать запросы. Поэтому на стороне Python-приложения реализован умный цикл повторных попыток (`wait_for_vault`), что является стандартом отказоустойчивости.

### Проверка сохранения секрета через Vault CLI
Чтобы убедиться, что секрет действительно надежно сохранен в хранилище, я зашел в контейнер Vault, переопределил протокол на HTTP (так как используется Dev-режим без TLS) и прочитал секрет напрямую через встроенный CLI-клиент:
```bash
docker exec -it vault-dev sh
export VAULT_ADDR=http://127.0.0.1:8200
vault login myroot
vault kv get secret/my_app_secrets
```

### GitHub Secrets vs HashiCorp Vault
Утверждать, что хранение секретов в GitHub Secrets — это "bad practice", технически некорректно, так как это индустриальный стандарт для малых и средних проектов. 

Однако в Enterprise-среде GitHub Secrets становится **менее масштабируемым и менее гибким подходом** по сравнению с dedicated-решениями (Vault, AWS Secrets Manager).

**Преимущества Vault:**
1. **Dynamic Secrets.** Vault умеет не просто статично хранить пароли, но и генерировать временные креды "на лету" (например, создавать юзера в PostgreSQL с TTL на 1 час). Если такой секрет утечет, он быстро станет невалидным.
2. **Single Source of Truth.** Если 50 микросервисов используют одну БД, пароль меняется в одном сейфе Vault. В случае с GitHub пришлось бы обновлять Secrets в 50 репозиториях.
3. **Строгий аудит.** Vault логгирует каждый чих: какой сервис, по какому токену и в какую секунду прочитал секрет. GitHub Secrets такого гранулярного контроля не дает.
